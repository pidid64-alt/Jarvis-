# Дизайн: несколько команд за одну реплику + гибридный fast-path

Дата: 2026-08-25
Статус: утверждён пользователем

## Проблема

1. Джарвис исполняет только одно действие на реплику. «Открой дискорд и какая
   погода» — выполняется что-то одно (в логе LLM даже начинает рассуждать
   текстом вместо JSON на таких фразах).
2. После миграции на OpenRouter каждая реплика ждёт облачный LLM:
   медиана 3.9 с, p90 10.2 с, max 18.5 с (35 замеров из jarvis.log).
   Раньше whitelist-matcher отвечал мгновенно.

## Решение (подход A, утверждён)

Три изменения: массив действий от LLM, точный fast-path без LLM,
мульти-exact в локальном matcher'е.

### Поток обработки реплики (jarvis.py `handle_voice_command`)

```
текст от STT
   │
   ├─ 1. Точные фразы команд в тексте? ──да──▶ выполнить все подряд (без LLM)
   │        нет (или слишком много лишних слов)
   ├─ 2. try_llm_route → список действий ──ок──▶ исполнить по порядку
   │        ошибка / лимит / мусор
   └─ 3. fuzzy-matcher — как сейчас, одиночный результат
```

Шаг 1 восстанавливает до-LLM скорость для известных фраз; шаг 2 добавляет
мультикоманды для свободной речи; шаг 3 — прежний fallback при 429/нет сети.

### Мульти-exact matcher (`match_commands_exact`)

- Находит ВСЕ фразы команд, целиком содержащиеся в тексте.
- Жадный выбор непересекающихся вхождений от самой длинной фразы.
- Дедуп по id команды (одна команда — один запуск).
- Порядок исполнения — по позиции в тексте.
- Защита от «проглатывания»: шорткат применяется только если суммарное число
  слов вне найденных фраз ≤ `exact_max_extra_words` (конфиг, default 6).
  Иначе реплика уходит на шаг 2 (LLM).
- Fuzzy-ветка существующего `match_command` не меняется и остаётся одиночной.
- Подтверждения dangerous-команд работают как раньше: голосовое «да» на каждую
  по очереди (последовательно внутри handle_command).

### LLM-схема: массив действий (llm_parser.py)

Ответ LLM:

```json
{"actions": [
  {"action": "command", "id": "<id>", "needs_confirmation": false},
  {"action": "speak", "text": "..."},
  {"action": "ask", "text": "..."}
]}
```

- Максимум `MAX_ACTIONS = 4`; лишние отбрасываются с warning в лог.
- Обратная совместимость: одиночный объект старого формата оборачивается в
  список из одного элемента; `{"actions": ...}` и голый объект принимаются оба.
- Каждый элемент валидируется неизменной `_validate_action` (whitelist-id,
  dangerous/confirm форсирует needs_confirmation=true) — безопасность не меняется:
  shell от LLM по-прежнему не приходит, только id или текст для TTS.
- Промпт дополняется правилом: несколько просьб в одной реплике → массив
  действий в порядке произнесения; одна просьба → массив из одного элемента.

### Исполнение списка действий (jarvis.py `try_llm_route`)

Действия исполняются последовательно, каждое озвучивает свой ответ
(решение пользователя: «по очереди», не склеивать).

Диалоговое состояние (`conversation_state`):
- реплика пользователя пишется один раз;
- каждый speak/ask пушится как реплика ассистента; pending ставит последний ask;
- если среди действий есть command — pending закрывается (как сейчас);
- демон продолжает слушать цикл (handle_voice_command → True), если в списке
  был хотя бы один speak/ask; только команды → False.

### Ошибки и границы

- Любая ошибка LLM (сеть, 429, битый JSON, пустой/невалидный массив) →
  fallback на шаг 3, пользователь ничего не замечает.
- Таймауты/ретраи LLM не трогаем (пользователь выбрал чистый гибрид);
  опциональный следующий шаг — `max_retries: 0` для быстрого fallback.

### Конфиг (DEFAULT_CONFIG / config.json)

- `exact_max_extra_words`: 6 — лимит «лишних» слов для fast-path.

### Тесты

- Парсер: массив из N действий; legacy-одиночка; fenced JSON; кап >4;
  невалидный id → LLMError.
- Matcher: перекрывающиеся фразы (длинная побеждает); две непересекающиеся
  команды; превышение exact_max_extra_words → пустой список; дедуп по id.
- Ручной e2e: `venv/bin/python3 jarvis.py --once --debug` +
  `scripts/test_llm.sh`.

## Не входит в объём

- Ужатие системного промпта (~11k токенов) и ретраев LLM.
- Мульти-fuzzy (несколько fuzzy-совпадений) — опасно по ложным срабатываниям.
- Сплит реплики по союзам.
