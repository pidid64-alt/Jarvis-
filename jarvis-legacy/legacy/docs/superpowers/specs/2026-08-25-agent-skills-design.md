# Дизайн: «реши проблему» (делегация Claude Code) и веб-поиск

Дата: 2026-08-25
Статус: утверждён пользователем (подход A)

## Проблема

Два новых агентских умения:
1. «Реши проблему» — Джарвис читает активный терминал и передаёт проблему
   тому, кто её исправит.
2. «Поищи инфу о X» — веб-поиск: краткий голосовой ответ ИЛИ открытие
   браузера; что именно — решает LLM.

## Решения пользователя

- Исправляет **Claude Code** (делегация), не сам jarvis — своя система
  разрешений, всё видно в терминале. Принцип проекта «текст никогда не
  становится shell-командой» сохраняется: передаётся ТЕКСТ ЗАДАЧИ, а не команда.
- При поиске **LLM сам решает**: ответить голосом или открыть браузер.
- Архитектура — гибрид A: solve через whitelist+fast-path (мгновенно, без
  трат лимита), search через новый LLM-action.

## Компонент 1: solve_terminal.sh + whitelist

Поток: голос «реши проблему» → exact fast-path → `scripts/solve_terminal.sh`:

1. Активное окно должно быть терминалом (`xdotool getwindowclassname`;
   иначе — notify и выход).
2. Снять текст буфера: Ctrl+Shift+A (select all), Ctrl+Shift+C (copy),
   `xclip -o -selection clipboard`; берём ПОСЛЕДНИЕ ~3000 символов (ошибки
   внизу). Старый клипборд сохраняем и восстанавливаем после печати задачи.
3. Сессия кодинга: если `coding_session.json` активен и окно живо —
   используем; иначе вызываем готовый `start_coding_session.sh`.
4. В вкладку Claude печатается ОДНОЙ строкой (новlines → пробелы, чтобы
   Enter в claude TUI не сработал раньше времени):
   `Вот вывод моего терминала, разберись и исправь под моим контролем: <текст>`

Требования: `xclip` (установить через pacman), `xdotool`, `claude` CLI — есть.

commands.json:
```json
{"id": "solve_terminal",
 "phrases": ["реши проблему", "реши ошибку", "исправь ошибку"],
 "command": "bash $HOME/jarvis/scripts/solve_terminal.sh",
 "response": "Читаю терминал и передаю задачу Клоду.",
 "min_score": 0.8}
```

## Компонент 2: веб-поиск через LLM-action

Новый тип действия в llm_parser/jarvis:

```json
{"action": "search", "query": "<тема>", "open": true|false}
```

- LLM ставит `open=true`, когда пользователь просит открыть сайт/гайд,
  `false` — когда нужен быстрый ответ.
- Валидация как у остальных actions: query непустой, ≤300 символов;
  open — bool, default false. Shell по-прежнему от LLM не приходит.

Исполнение (`handle_search`):
1. `web_search.py`: `search_snippets(query, n=5)` через библиотеку `ddgs`
   (DuckDuckGo, бесплатно, без ключа) — title/body/href.
2. `open=false`: суммаризация топ-сниппетов тем же free-LLM (≤500 символов,
   ~1 запрос лимита OpenRouter) → speak. Fallback при ошибке LLM: озвучить
   заголовки сниппетов.
3. `open=true`: `xdg-open https://duckduckgo.com/?q=<urlencoded>` +
   короткое «Открываю результаты».
4. Диалоговое состояние: summary пушится как реплика ассистента (диалог
   продолжается); при open — как командное действие.

Ошибки: ddgs недоступен/нет сети → speak «Поиск недоступен»; пустая выдача →
«Ничего не нашёл». Ничего не падает.

## Зависимости

- `xclip` — pacman (нужен sudo пользователя).
- `ddgs` — pip в venv jarvis (без sudo).

## Тесты

- web_search: мок ddgs → структура сниппетов; пустая выдача.
- llm_parser: action=search валиден; query-ограничения; open default false.
- solve_terminal.sh: DRYRUN-режим (печатает план вместо xdotool-действий).
- Живой e2e — вручную пользователем (голосом).

## Не входит в объём

- Свой мини-агент с исполнением команд от LLM (отклонено пользователем).
- Локальная SearXNG (RAM-бюджет машины).
- Автоподстановка вопросов к поиску, кэш выдачи.
